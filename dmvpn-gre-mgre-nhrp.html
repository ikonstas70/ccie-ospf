DMVPN — GRE, mGRE & NHRP

How a hub with a single tunnel interface reaches dozens or hundreds of spokes without ever naming their addresses in its configuration — and why that's really just an overlay↔underlay translation problem.

CCIE Enterprise Infrastructure · DMVPN / Tunneling
GRE mGRE NHRP DMVPN Phase 2/3 Overlay / Underlay
Point-to-Point GRE

A classic GRE tunnel connects exactly two endpoints, and Cisco needs to be told exactly where the far end is:

R1 configuration 
interface Tunnel0
 tunnel source GigabitEthernet0/0
 tunnel destination 2.2.2.2

There is only one possible destination, so tunnel destination is mandatory. Cisco has no other way to know where the tunnel packets should go.

The mGRE Problem

Now put one hub in front of many spokes:

              HUB
             / | \
            /  |  \
          S1  S2  S3 ... S100

A single tunnel interface can't carry a single tunnel destination — there's no one answer to "which spoke?" So Cisco removes the statement entirely and switches the interface into multipoint mode:

Hub configuration 
interface Tunnel0
 tunnel mode gre multipoint

No tunnel destination appears anywhere on the hub. One interface can now reach Spoke1, Spoke2, Spoke3 … Spoke100 — but only if something else tells it where each spoke actually lives.

NHRP Resolves the Destinations

That "something else" is NHRP (Next Hop Resolution Protocol). Each spoke registers its tunnel (overlay) address against its real (underlay) address with the hub:

SpokeTunnel IP (overlay)Physical IP (underlay)
Spoke110.0.0.11200.1.1.11
Spoke210.0.0.12200.1.1.12
Spoke310.0.0.13200.1.1.13

The hub builds this mapping dynamically through NHRP registration — it never needs the spoke addresses typed into its configuration. That's the whole point of the three protocols working together:

  • GRE — creates the tunnel
  • mGRE — lets one tunnel interface have many destinations
  • NHRP — discovers where those destinations actually are

That's why a DMVPN hub's running config shows tunnel mode gre multipoint but never a tunnel destination — NHRP is telling mGRE where the spokes are, dynamically, at runtime.

NHRP as Overlay↔Underlay Translator

The cleanest mental model for NHRP is as a translator sitting between two networks:

Overlay
The network your routing protocol actually sees — tunnel addresses like 10.0.0.1, 10.0.0.11, 10.0.0.12. OSPF, EIGRP, or BGP run here.
Underlay
The real transport network — in most DMVPN labs, public Internet IPs like 100.1.1.1, 200.1.1.11, 200.1.1.12. This is what the ISP actually routes.
NHRP database
The mapping between the two: 10.0.0.11 → 200.1.1.11, 10.0.0.12 → 200.1.1.12, learned dynamically from spoke registration.

A precise, exam-ready definition:

NHRP resolves DMVPN overlay tunnel addresses into underlay transport addresses, allowing mGRE tunnels to dynamically discover and reach remote spokes.

Many engineers anchor this with a one-line analogy:

ARP : Ethernet :: NHRP : DMVPN. Both translate a logical address into a physical one — ARP maps an IP to a MAC on a LAN segment; NHRP maps a tunnel (overlay) IP to a transport (underlay) IP across a DMVPN cloud. Different layers, same job.

What the Underlay Actually Is

In the overwhelming majority of DMVPN labs and real deployments, the underlay is the public Internet — so "underlay = public IPs" is a safe shortcut to memorize. But the formal definition is broader:

Underlay = whatever network is responsible for transporting the tunnel packets.

That can equally be MPLS, a provider WAN, a private WAN, or a cloud provider's network — the underlay is a role, not a specific address space. DMVPN just happens to be built on top of it most often over the public Internet.

One-Minute Summary
  • Point-to-point GRE always needs a manually configured tunnel destination — there's exactly one peer, so nothing needs to be discovered.
  • mGRE removes tunnel destination entirely because one tunnel interface serves many peers, and no single address would be correct.
  • NHRP fills the gap mGRE leaves behind: spokes register tunnel IP → physical IP, and the hub (and other spokes, in Phase 3) build a dynamic resolution table from those registrations.
  • Overlay = tunnel addresses, where routing protocols live. Underlay = transport addresses, almost always public IPs in lab scenarios, but formally just "whatever carries the tunnel traffic."
  • NHRP is the overlay↔underlay translator — the same conceptual job ARP does for IP↔MAC on Ethernet.
